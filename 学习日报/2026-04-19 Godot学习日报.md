## 今日学到的 Godot/GDScript 知识点

### 敌人战斗反馈

本次把敌人的受击体验补齐了一层：受到伤害时生成血液特效，并通过资源和场景组合把视觉反馈从伤害逻辑里拆出来。这个方向很好，因为战斗系统不只是数值扣减，还需要给玩家明确反馈。

相关理解：

- `PackedScene` 适合封装血液、生成标记、死亡粒子等一次性效果。
- 伤害逻辑可以只负责判断和触发，具体视觉表现交给独立场景处理。
- 敌人死亡需要 `is_killed` 这类状态保护，避免多次触发死亡效果或重复掉落。

### 可选组件设计

敌人武器控制器被改成可选组件后，近战敌人可以不装备武器。这是组件化设计里很重要的一步：不是所有敌人都必须拥有同一套子节点，脚本应该允许场景差异存在。

这带来的 GDScript 习惯是：

```gdscript
if weapon_controller == null:
    return
```

这种防御不是为了掩盖错误，而是表达“这个组件在设计上允许不存在”。和必须存在的组件相比，可选组件最好配测试，今天新增的 `test_enemy_weapon_controller_optional.gd` 就是在保护这个约定。

### 调试面板

F3 调试面板把敌人生成状态、音频播放等运行时信息直接显示出来。对 Godot 游戏来说，这比反复 `print()` 更适合中后期开发，因为调试信息可以和游戏画面同时观察。

今天的理解：

- 调试 UI 适合放在 Arena 这类运行时管理场景里。
- 生成器需要暴露“是否已经生成”“当前房间状态”“敌人数量”等可观察数据。
- 调试信息应该服务于定位问题，后续可以统一挂到 debug 开关下。

### 硬币与商店交互

硬币系统引入了完整的拾取链路：硬币场景、拾取逻辑、全局金币数、UI 显示、音效和事件总线信号。商店物品则开始处理稀有度显示和购买交互。

关键点：

- `Global.coins` 适合先作为原型阶段的全局状态，但后续可以拆到更专门的经济系统。
- `EventBus` 适合广播金币变化，让 UI 不需要主动查询金币数。
- 新增“互动”输入映射后，商店购买可以和射击、移动分离，避免操作语义混在一起。

## 代码或场景改动带来的理解

### 1. 从“测试摆放”走向“系统生成”

`level_01_room.tscn` 里今天先加入过测试硬币实例，当前未提交改动又把这些硬币节点移除了。这说明硬币已经从“放几个在房间里试效果”进入下一阶段：应该由房间奖励、宝箱、商店或敌人掉落系统来生成，而不是长期写死在基础房间场景里。

### 2. 经济系统需要事件边界

金币数量变化是一个跨系统事件：硬币场景负责拾取，Global 保存数量，UI 显示数值，商店读取余额。这里如果互相直接引用会很快混乱，用 `EventBus` 发出金币变化信号是比较干净的方向。

### 3. 商店物品是数据驱动的自然延伸

`ItemData` 和药水资源出现后，商店不必把“价格、稀有度、图标、效果”写死在节点脚本里。它可以像 `PlayerData`、`WeaponData` 一样，走 Resource 配置路线。

## 遇到的问题与解决方式

- 敌人生成可能重复触发：通过增强 `enemy_spawner.gd` 的生成状态和调试统计来观察并规避重复生成。
- 近战敌人不一定有武器控制器：把武器控制器改为可选组件，并补测试锁住行为。
- 房间进入检测可能被非玩家触发：改进检测逻辑，只让玩家进入时触发房间事件。
- 商店和硬币需要新的操作语义：在 `project.godot` 中添加“互动”输入映射，避免和射击输入混用。
